How to Cut Node.js API Latency: What Actually Worked

Measure first, fix the database second, cache third. The order matters.

On a high-traffic ordering platform for a coffee chain with 500+ stores (case study), our team cut API latency by about 30% and database load by about 40%. None of it was magic. Here is the order of work I'd follow on any Node.js backend.

1. Measure before you change anything

Add distributed tracing (we used OpenTelemetry with Jaeger) so you can see where each request spends its time across services. In almost every slow API I've seen, the time goes to a handful of database queries or to calls made one after another that could run together.

2. Fix the slow queries

  • Turn on the slow-query log and sort by total time, not just the slowest single query.
  • Run EXPLAIN on the worst ones. Missing or wrong indexes are the most common cause.
  • Remove N+1 patterns: one query for a list, then one query per item. Fetch them in one go.
  • Select only the columns you need, and paginate anything that can grow.

3. Cache what is read often and changes rarely

Menus, prices, store details and configuration are read on almost every request but change rarely. Caching them in Redis with a clear expiry and invalidation on change takes a lot of load off the database. Don't cache everything: stale data in the wrong place causes worse bugs than slowness.

4. Move slow work off the request

Sending notifications, awarding rewards or calling slow third-party APIs doesn't need to happen before the user gets a response. Put it on a queue (Bull or BullMQ on Redis) and let workers handle it.

5. Keep watching

Performance drifts as features are added. Keep the tracing, set alerts on response times, and check the slow-query log every few weeks.
