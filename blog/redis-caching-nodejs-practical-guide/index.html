Redis Caching in Node.js: What to Cache and What Not To

Caching is the quickest way to speed up an API and the quickest way to show users wrong data. The rules I follow so I get the first without the second.

On a busy ordering platform, a big part of our latency win came from caching data that every request read but that rarely changed: menus, prices, store details, configuration. It's also where I've seen the strangest bugs, usually a price that changed in the database but not in the app. These are the rules I use now.

Start with cache-aside

The simplest pattern: on a read, check Redis; if the value is there, return it; if not, read the database, store the result in Redis with an expiry, and return it. On a write, update the database and delete the cached key. Ninety percent of the time this is all you need.

Pick TTLs on purpose

  • Configuration and menus: minutes to hours, plus deletion when they're edited.
  • Lists and search results: seconds to a minute.
  • Anything a user just changed: don't rely on TTL, delete the key on write.

Name keys so you can find them

I use names like store:42:menu:v3. The version at the end lets me change the shape of cached data without old entries breaking the new code; I just bump the version.

Protect against a stampede

When a popular key expires, hundreds of requests can hit the database at the same moment. A short lock, so only one request rebuilds the value while the others wait or get the old value, prevents that spike.

What I never cache

  • Payment status and wallet balances. Always read them from the source.
  • Anything with permissions baked in, unless the key includes the user or role.
  • Data you can't explain how to invalidate. If you can't say when it goes stale, don't cache it.

Caching is step three, after measuring and fixing slow queries (the full order). Need a faster API? See backend development.
