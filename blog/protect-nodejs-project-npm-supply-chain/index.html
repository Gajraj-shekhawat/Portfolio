How to Protect a Node.js Project from npm Supply-Chain Attacks

Attacks through hijacked npm packages keep making the news. Ten practical habits that make your project a much harder target.

A supply-chain attack is when an attacker gets malicious code into a package you install, often by taking over a maintainer's account or publishing a look-alike name. Your own code can be perfect and still be compromised. These habits make a big difference and cost almost nothing.

Ten practical habits

  1. Commit your lockfile (package-lock.json, pnpm-lock.yaml or yarn.lock) so every install gets exactly the same versions.
  2. Use npm ci in CI and production, not npm install. It installs strictly from the lockfile.
  3. Use fewer dependencies. Before adding a package for a few lines of code, write the few lines yourself.
  4. Check new packages before installing: spelling of the name, weekly downloads, recent maintainers, and the repository link.
  5. Turn off install scripts where you can (--ignore-scripts), and allow them only for packages that truly need them.
  6. Update on purpose, not by accident. Use Dependabot or Renovate to raise update pull requests you can review, rather than wide version ranges.
  7. Run npm audit (or a similar scanner) in CI and fix high-severity issues.
  8. Turn on two-factor authentication for your npm and GitHub accounts, and for everyone who can publish or merge.
  9. Keep secrets out of CI steps that install packages, and give CI tokens the smallest permissions possible.
  10. Watch production: unusual outgoing network calls from your server are often the first sign something is wrong.

If you think you've been hit

  • Pin back to the last known-good lockfile and redeploy.
  • Rotate every secret the server or CI could read: database passwords, API keys, tokens.
  • Check logs for unexpected outgoing connections and new files.
