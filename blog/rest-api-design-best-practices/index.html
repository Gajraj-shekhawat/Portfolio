REST API Design That Doesn't Break: 8 Practical Rules

Good APIs are boring in the best way: predictable, documented and hard to misuse. Eight rules I follow on every backend.

An API is a promise to every app that uses it. Break it and mobile apps in your users' pockets break too, because they can't all update at once. These are the rules I follow to keep APIs stable and easy to use.

Eight rules

  1. Use clear, plural resource names: /orders, /orders/{id}, /orders/{id}/items.
  2. Validate every input at the edge with a schema, and reject unknown fields. Never trust the client.
  3. Return one consistent error shape, for example { "error": { "code": "ORDER_NOT_FOUND", "message": "..." } }, with correct HTTP status codes.
  4. Paginate every list; cursor-based pagination stays fast as data grows.
  5. Make writes idempotent: accept an idempotency key on payments and order creation so retries never create duplicates.
  6. Version deliberately: add fields freely, never remove or rename them without a new version, and give old apps time to move.
  7. Keep auth and permissions on the server: check who the user is and what they may do on every request.
  8. Document it: an OpenAPI spec generated from the code, with example requests and responses.

For mobile apps especially

  • Return only what the screen needs; big responses are slow on mobile networks.
  • Send a minimum supported app version so you can force updates when an old app would break.
  • Log the app version with every request; it makes debugging much faster.
