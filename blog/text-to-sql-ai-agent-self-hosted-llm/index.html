Building a Text-to-SQL AI Agent on a Self-Hosted LLM

Plain-English questions over 1.7 million school records, answered by a model that runs on our own GPU, which only switches on when someone asks.

Most people who need answers from a database can't write SQL. For Yugam International School I built Yugam Ask, an AI agent that answers questions about India's 1.7 million schools in plain English. Here is how it works and what I learned building it.

The problem

The team wanted quick answers from the public UDISE schools dataset: how many CBSE schools are in a district, which blocks have the most private schools, how enrolment compares across states. The data was all there, but every question meant asking an engineer to write a query. Sending school data to a third-party AI API was not an option, and an always-on GPU would have cost too much for occasional use.

How the agent works

  1. Understand the question. The model gets the question, a short description of the tables and columns, and a few worked examples.
  2. Write read-only SQL. It produces one SELECT query. Before anything runs, the query is checked: only SELECT is allowed, only known tables, and a row limit is added.
  3. Run it safely. Queries run on PostgreSQL under a read-only database user, so even a bad query can never change data.
  4. Explain the answer. The result goes back to the model, which answers in plain English and shows the numbers it used.
  5. Remember context. Per-user memory makes follow-ups like "and in Jaipur?" work naturally.

Running the model ourselves

The agent uses an open-weights Qwen model served with vLLM on a rented GPU. A small gate in front of it starts the GPU when the first question arrives and shuts it down after a quiet period. Users wait a little longer for the first answer of the day, and in return the GPU only costs money while someone is actually using it.

Keeping the data fresh

The school data lives in MongoDB for the main apps. A nightly job copies it into PostgreSQL, which is far better for the aggregate queries people ask. The agent always queries PostgreSQL, so the main apps are never slowed down.

What I'd tell anyone building one

  • Guardrails matter more than prompts. A read-only user plus a query check catches what the model gets wrong.
  • Give the model a clean, well-named schema. Renaming confusing columns improved accuracy more than any prompt change.
  • Show the numbers behind every answer, so people can trust them or spot a mistake.
  • You don't need a third-party AI provider for this. A self-hosted model keeps data private and costs stay predictable.
